File sizes in Find in Files

CEN 4021, Software Engineering II, Spring 2015: a change request against a real codebase. Thirteen lines added to Notepad++, handed in on 24 April 2015 as one source file and a write-up.

Change request. Using Find in Files, Notepad++ users can see the full file paths of the files that contain the searched string. Allow the users to view also the size of the files in the results.

Notepad++ is a Windows program built with Visual Studio, so this one is not running here — a 2015 Win32 build in a browser is not something this site can do without becoming a different site. What it can do is show the change exactly.

The diff

Generated by this site's image build, against the file as Notepad++ shipped it. Which release? The submitted file differs from FindReplaceDlg.cpp in 6.7 through 6.7.4 — identical in all five; upstream did not touch it between October 2014 and February 2015 — by exactly these thirteen lines, and from every later release by hundreds. So the base is 6.7.4, from January 2015, three months before the due date. Line endings are stripped for display; both files are CRLF.

The write-up (PDF) has four sections: concept location, impact analysis, implementation and testing. The file-size code was lifted from loadFileData() in the same codebase, and testing was a search of the whole C: drive for “test”, with the reported sizes compared against the files on disk.

Notes, eleven years on

  • “Only called in a single spot” was true, and not the whole story. The impact analysis found the one call site of Finder::addFileNameTitle(). But that site is FindReplaceDlg::processAll(), and in 6.7.4 three commands go through it: Find in Files, Find All in Current Document and Find All in All Opened Documents. All three print the size now.
  • For the other two, the size can be wrong. Those pass the open buffer's path, and the new code measures the file on disk. Edit a document without saving and its result header reports the size it had when last saved.
  • And for an unsaved tab, there is no file. generic_fopen returns NULL, and the next line hands that straight to _fseeki64. The Visual C++ runtime treats a null stream as an invalid parameter, and its default handler ends the process. That is from reading the code against the 6.7.4 sources, not from running it — there is no Windows build here to try it in.
  • “KB” is 1,024 bytes, to two decimal places, so a 1,000-byte file reads (0.98 KB).
