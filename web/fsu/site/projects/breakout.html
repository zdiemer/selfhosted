Breakout

Java Swing, Fall 2014. A pair project with Adam Greenstein — the README still carries the “Division of Labor” section we were asked to write. Adam took the game engine and level editor; I took the menus, the layout and the bug-fixing.

Loading a JVM into your browser…

Playing it

Left and Right move the paddle, Space launches the ball, Esc pauses. Click the game area first — it needs keyboard focus, and while it has focus the arrow keys and space will not scroll this page.

Save and load work, which I did not expect. The 2014 code does new FileOutputStream("breakout.sav") relative to the working directory; under CheerpJ that directory is a writable, IndexedDB-backed virtual filesystem, so the save lands in your browser rather than on the server and survives a reload. Pause with Esc and the pause menu's Save Game really does put up its “Game Saved” dialog. The level editor works too.

One quirk of the original worth knowing: pressing Space to launch the ball calls manager.setCanSave(false), so a game can only be saved before the ball is in play. That is 2014's decision, not the browser's.

Quit exits the JVM, not a window. The menu buttons call System.exit(0), which in a tab means the whole runtime stops and the black rectangle above simply goes dead. Reload the page to start over. That is the original behaviour meeting a context it was never written for, and it is left alone.

What it is

Source
github.com/zdiemer/Breakout — 24 classes, one package, first commit 18 Nov 2014, last 5 Dec 2014.
Toolkit
Plain Swing. A JFrame with a CardLayout of screens, and a JLayeredPane playfield where the ball, paddle and every brick are each their own JPanel overriding paintComponent. Not an applet, no ACM library, no third-party jars at all.
Game loop
A javax.swing.Timer(10, …) on the event dispatch thread — nominally 100 frames a second.
Assets
One: a hand-drawn ball.png. No sound.
Build
None in the repo. No Makefile, no Ant, no Maven, no jar — the README says to “click on the compiled jar file” and the jar was never committed. It is built here with javac --release 8.

Notes, eleven years on

  • The resource path is a trap. Ball.java does getResource("/images/ball.png") with a leading slash, so images/ has to sit at the root of the jar, beside breakout/ rather than inside it. Get it wrong and ImageIO.read returns null, the constructor's catch block prints the exception to a stdout nobody is reading, and the very next line throws again. The game dies before the window appears. The build asserts the entry's position rather than trusting it.
  • The window height is load-bearing. Ball.setPosition computes frame.getHeight() - 480, so the physics assume the frame is exactly the 480 pixels it was set to in 2014. The frame is non-resizable, which is the only reason that was ever fine.
  • Nine deprecated boxing constructors. new Integer(30) for the JLayeredPane layer arguments. Deprecated for removal since JDK 9 — which is part of why this is compiled against Java 8, where the call is still ordinary.
  • No serialVersionUID anywhere, on five Serializable classes that a save file is written from. A save made by one build would not necessarily load into the next. Nothing forced the issue because nobody kept a save.
  • The frame rate is aspirational. A 10 ms Swing timer on the EDT was already optimistic in 2014; under a JVM that is itself compiled to WebAssembly it settles wherever the browser's animation frames land. The game is frame-rate-dependent, so it plays a little differently here than it did on a lab machine. That felt more honest than retuning the constants.
