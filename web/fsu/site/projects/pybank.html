pybank

“A Django and Python powered online banking system.” Spring 2016, a team project with Wenqi Wang. The last commit is titled Final functionality push before presentation tomorrow, which tells you most of what you need to know.

Open the bank

Sign in as demo / seminoles. There is a second account, alex, with the same password, so the transfer-to-another-user flow has somewhere to send money. Both start funded.

The database is recreated from scratch every time the pod restarts, and it lives in memory rather than on a disk. Move the fake money around as freely as you like.

Running Python 2.7 on purpose

This one could not be modernised without editing it, and the rule for this site is that the repositories are not edited. Two things pin it: main/views.py does import account_type — an implicit relative import, which is Python 2 syntax and a ModuleNotFoundError on Python 3 — and the same file mixes tabs and spaces for indentation, which Python 3 rejects at parse time before it ever gets that far.

So it runs where it ran: Python 2.7.18 and Django 1.9.5, on Django's development server, with DEBUG = True. That is not nostalgia cosplay — runserver with DEBUG on is the only thing serving the stylesheets, and the yellow Django error page is part of the exhibit. The SECRET_KEY has been sitting in the public repository since 2016, so there is no secret left to protect; what makes this acceptable is that the host is unreachable off my tailnet, the container has no network access and a read-only filesystem, and the entire database is fake.

Two things were changed, both in the container image and neither in the repository: jQuery was vendored locally because the page loaded it over plain http:// and a browser will not do that on an HTTPS site, and a dead FontAwesome <link> was dropped — its CDN was shut down in 2024 and a search of every template finds not one fa fa- class using it.

What it is

Source
github.com/zdiemer/pybank — 6 Apr to 19 Apr 2016.
Model
One. Account: a user, a 16-digit card number, an IntegerField balance, a type discriminator for savings/checking/credit, an activation flag and a PIN.
Features
Register, log in, deposit, transfer between your own accounts, transfer to another user, open a credit card, pay it off, spend against a card number and PIN, and change your email or password.
Frontend
UIKit 2.x, vendored into the repo.

Notes, ten years on

  • Money is an IntegerField. Whole dollars, no cents. Not a demo simplification — that is what the model declares.
  • PINs are stored in clear text in a CharField(max_length=4), next to a card number that is also in clear text. Passwords are hashed, because Django did that part for us.
  • There is no ledger. No Transaction model, no history, no audit trail: a transfer reads two integers, adds and subtracts, and saves. There is nothing to reconcile against and no way to see what happened.
  • Five bare except: pass blocks in a single view. IndexView.post is one handler for every action on the dashboard, working out what you meant from which POST keys are present, with each branch wrapped in a bare except. Anything that goes wrong looks exactly like nothing happening.
  • Logged out, it still shows you an account. Open the bank without signing in and you get “Your Account”, Savings and Checking, each reading $0. views.py:13 tests if user.is_authenticated: without the parentheses — in Django 1.9 that attribute is a bound method, and a method object is always truthy, so the branch runs for anonymous visitors too. Every Account.objects.get inside it then raises, and the bare excepts turn each one into the string '$0'. Fifty lines further down, views.py:56 calls the same thing correctly, with ().
  • The site root has always been a 404. pybank/urls.py mounts the app at ^main/ and the admin at ^admin/ and defines nothing for ^$. The link above goes to /pybank/main/ for that reason.
  • The first migration creates Question and Choice — the models from the Django tutorial's polls app, scaffolded and never cleaned up. The second migration deletes them both. You can read the first week of the project in the migration history.
  • Two migrations contain a hard-coded card number ('1555363332285110'), because at the moment makemigrations ran, the field's default was a function call, and Django froze the value it returned.
  • Balances render as currency through the C library. views.py calls locale.setlocale(LC_ALL, '') and then locale.currency() — and the second one is inside one of those bare excepts. In a container with no generated locale, every balance on the site silently renders as $0 and the page looks fine. The image generates en_US.UTF-8 specifically so that does not happen.
