# egress-proxy

The cluster's single **egress** choke point — the counterpart to what `infra/traefik` is for ingress. A CONNECT-only forward proxy that services opt into, so outbound traffic becomes attributable, measurable, and movable off the home address.

```
opted-in pod ──http──▶ egress-proxy.infra.svc:3128 ──┬─ lane: direct ──▶ the house
   (authenticates as itself)                          └─ lane: vps ─────▶ a VPS exit
```

## Why

Three problems, one shape:

1. **Everything left from the house.** `games/gamedex` talks to ~50 hosts, `finance/money` scrapes Zillow and Redfin, `web/apartment-watch` scrapes Craigslist and Zumper, and `discord/smitele-bot` pulls ~118 GB/month through a Cloudflare-fronted tracker.gg — all from the address the household browses from. smitele-bot has already been refused with `Retry-After: 3600`, which [its own docs](../../discord/smitele-bot/docs/proxy-setup.md) correctly read as a ban on the address rather than a rate limit.
2. **Proxying was being reinvented per service.** smitele-bot has a careful egress abstraction; talaria has an unrelated one with three provider backends; `finance/money` has a third and cruder one. None share anything, and two were unconfigured in-cluster.
3. **NetworkPolicy cannot express a hostname.** k3s does enforce NetworkPolicy (kube-router's controller, embedded in the agent) but only at L3/L4. Six charts here hand-roll the same `0.0.0.0/0 except RFC1918` block, each with a comment apologising that hostnames aren't matchable.

## The design spine: `lane: direct` means "measured, but unchanged"

A service opts in for attribution and byte accounting **with no change to where its traffic exits**, and moves to a different exit later as a one-word change. Measuring and changing address are separate decisions, which is what makes this safe to roll out one service at a time.

## It is a blind tunnel, and must stay one

There is no `ssl_bump` and no TLS interception in the rendered config, and adding any would break the two most important clients *silently*:

- **smitele-bot** impersonates Firefox with `curl_cffi` and mints its Cloudflare clearance cookie in Camoufox. The cookie is bound to the TLS fingerprint that minted it.
- **talaria** pins JA3/JA4 through httpcloak, and its TODOs explicitly warn against proxies acting as HTTP/2-to-HTTP/1 gateways.

A CONNECT tunnel is opaque TCP: the client's handshake and its ALPN-negotiated h2 reach the origin untouched, and squid never parses a byte of either. Both concerns are satisfied by construction. `upgrade.sh` asserts this against the rendered config rather than trusting it.

`via off` and `forwarded_for delete` are set for a related reason — the defaults append `Via:` and `X-Forwarded-For: <pod IP>`, announcing the request as proxied and leaking internal addressing. Squid warns `HTTP requires the use of Via` on every parse; that warning is expected.

## Fail closed

Squid's default when a peer is unreachable is to go **DIRECT** — which would silently drop a service back onto the home address, the exact failure the lane exists to prevent, with no error and no log line that looks wrong. Every client routed to a peer therefore also gets `never_direct`, and `upgrade.sh` fails the deploy if any client is peered without it.

Each peer also gets a closing `cache_peer_access <peer> deny all` *after* the per-client allows, since peer selection is otherwise allow-by-default once a peer exists.

## Auth is attribution

Every client has a credential whose username is its chart name. The NetworkPolicy is the security boundary; the credential exists so each log line carries a durable service name instead of an ephemeral pod IP:

```
ts=1786121128.911 svc=smitele-bot lane=direct src=10.42.2.204 method=CONNECT \
  url=api.ipify.org:443 status=200 bytes_in=3581 bytes_out=1032 \
  peer=TCP_TUNNEL:HIER_DIRECT dst=104.26.13.205 duration=149
```

Passwords are generated by `upgrade.sh` into `values.local.yaml` and hashed into a Secret with `openssl passwd -apr1`, reusing the existing salt so an unchanged credential produces a byte-identical Secret. They are a **map keyed by client name**, never part of the `clients` list — Helm merges maps by key but replaces lists wholesale, so a password added to a list would silently drop every other client.

## Opting a chart in

```yaml
egress:
  proxy:
    enabled: true
    lane: direct
    mode: env        # env | explicit
  allowedHosts: []
```

The release renders `Secret/egress-proxy-client` into the client's namespace (`url`, plus split `host`/`port`/`username`/`password` for consumers like Playwright that reject inline credentials). Pods must also carry `egress.zachd/proxied: "true"` — the NetworkPolicy selects on that label, so a pod without it cannot reach the listener at all. Charts stamp it from their own `egress.proxy.enabled`, so the allowlist cannot drift out of sync with reality.

**`mode` is not a style choice.** `discord/smitele-bot` must use `explicit`: it sets `trust_env=False` deliberately, because `curl_cffi` reads `HTTPS_PROXY` on its own and Camoufox does not, so an environment-set proxy would send the crawl through one address while the clearance cookie was minted at another — 403 on every request, twelve solves burned, four-hour breaker armed.

`NO_PROXY` in `env` mode is a chart constant, not a per-service value. It must always cover `.svc`, `.cluster.local`, `10.42.0.0/16`, `10.43.0.0/16` and `192.168.4.0/24`, or in-cluster calls (`money` → `gamedex.games.svc`, `apartment-watch` → `sms-relay.infra.svc`) route through squid and break.

## What must never be proxied

| Service | Why |
|---|---|
| `infra/duckdns` | Sends an empty `ip=` so DuckDNS records the **source** address. Proxying it repoints `zachd.duckdns.org` at the proxy and takes down every ingress in the cluster. |
| `infra/cloudflared`, `web/kelsey-green` | QUIC over UDP 7844. HTTP CONNECT does not carry UDP. |
| `infra/sms-relay` | Send path is a LAN address; its netpol allows RFC1918 deliberately. |
| `minecraft` | Latency-sensitive, and its inbound LoadBalancer is on the home IP anyway. |
| `dev/claude-workspace` Tailscale | Needs raw UDP to NAT-random peer ports. |
| `infra/buildkit` | Bursty multi-GB registry pulls would dominate the exit's bandwidth for no reputation benefit. |
| `discord/vocard` | YouTube blocks datacenter ASNs harder than residential ones — proxying makes playback worse. |
| `infra/alloy` | DaemonSet telemetry from all 10 nodes; volume without benefit. |

## Talaria (a different repo)

Talaria's chart lives at `/home/zachd/Code/talaria/helm/talaria`. Its `RotatingProxyManager` already reads a comma-separated `PROXY_LIST` with optional `?country=XX` and handles round-robin, geo preference and failure backoff — so a **one-element list pointing at this proxy is a valid config with zero code change**. Add it to `templates/_scraper-worker.tpl`'s env block.

Its rotating need is genuinely different from smitele-bot's sticky one, and the `residential` lane models that with `roundRobin: true` over N peers, which fits a Webshare-style endpoint list. **BrightData cannot be expressed as a peer**: its rotation encodes country and session in the *username*, per request, and a `cache_peer` carries one fixed `login=`. That one stays app-side.

## Deploy

```sh
./upgrade.sh
```

It generates missing client passwords, builds the htpasswd Secret, asserts the config invariants (blind tunnel, terminal deny, every peered client fails closed, every peer closed off), parses the rendered config with the real squid binary in a throwaway pod, applies, and then proves a request actually gets out and that an unauthenticated one is refused.

## Verify

```sh
kubectl -n infra logs deploy/egress-proxy --since=10m | grep '^ts='
```

A denied CONNECT is a transport failure, not an HTTP status — curl reports `CONNECT tunnel failed, response 407` and exits 56, and `%{http_code}` is `000` because no end-to-end response was received. Don't read that `000` as the proxy being broken.

## Known gaps

- **A brand-new pod's first request can be refused.** kube-router has to resolve the pod's labels into an ipset before the NetworkPolicy admits it. Measured here at well under two seconds — the request at t=0s fails, the one at t=2s succeeds — but a client that makes exactly one request in its first second would see it. Long-running crawls are unaffected; a single-shot CronJob should retry.
- **Squid's own DNS lookups are attributed to the proxy.** While an `infra/coredns-config` audit window is open, a proxied client's destination appears twice: once from the client, once from squid. Reach stays correct, counts double.
- **No metrics exporter.** Deliberate, for now: `squid-exporter` would add a third-party image for counters the access log already implies, and per-destination bytes have to live in the log anyway — a per-destination *label* is a cardinality bomb against Grafana Cloud's 10k-series free tier, by the same argument `infra/alloy` makes about `RequestPath`.
- **Health probes read `/proc/net/tcp` rather than connecting.** Squid logs every connection that opens and closes without a request as an aborted transaction, ~17k lines/day across two pods, and none of squid's access_log ACLs suppress them — the ACL is evaluated in a context with no HTTP request, so `method NONE` warns and logs anyway, and `src` does not take either. Not generating the transaction is the only thing that works. If those lines reappear, something really is dropping connections to the listener.
- **`allowedHosts` is empty for every client.** Fill it from a real measurement (`scripts/egress-audit.sh`), not from a guess. An allowlist written from imagination breaks the service at the worst moment and teaches everyone to widen it back to empty.
